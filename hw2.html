Homework 2 · Hashing, key derivation and cryptographic primitives

From wallet seed to Ethereum address

When a cryptocurrency wallet presents a twelve-word mnemonic phrase, subsequently derives an address such as 0x9858EfFD…EcaEda94. Between the two there is a chain of six standards, each doing one job. This page runs the chain live, explains the role of every piece, and measures the statistical properties each step relies on.

1. The pipeline, live

Every value below is computed in the browser from the phrase in the box. The default phrase is the public BIP-39 test vector (entropy = all zeros).

2. Role and purpose of each standard

BIP-39 · 2013

Mnemonic sentence and seed generation

Turns random bits into words a person can write on paper, and words into a seed.

  • 128 random bits + 4 checksum bits (the first bits of SHA-256 of the entropy) = 132 bits = 12 groups of 11 bits. Each group is the index of a word in a list of 2048.
  • Seed = PBKDF2-HMAC-SHA512(phrase, salt = "mnemonic" + passphrase, 2048 iterations) → 512 bits.

Purpose: a human-friendly, error-detecting backup of the wallet.

BIP-32 · 2012

Hierarchical deterministic (HD) key derivation

Grows a whole tree of keys from the single seed.

  • Master: HMAC-SHA512(key = "Bitcoin seed", seed) → left half = master private key, right half = chain code.
  • Child i: I = HMAC-SHA512(chain code, parent key ‖ i); child key = (Ileft + parent key) mod n.
  • Hardened children (marked ′) use the parent private key, so they cannot be derived from public data.

Purpose: one backup, unlimited accounts.

BIP-44 · 2014

Standard derivation paths

Says which branch of the BIP-32 tree a wallet must use:

m / purpose′ / coin_type′ / account′ / change / address_index

For Ethereum: m/44′/60′/0′/0/0 (coin type 60); the second account is …/0/1.

Purpose: interoperability. The same phrase gives the same accounts in any compliant wallet.

secp256k1 · 2000

Elliptic-curve public-key cryptography

The curve y² = x³ + 7 over a 256-bit prime field. Public key Q = kG: exactly Homework 1 at full scale.

  • Private key: a number in [1, n − 1], 256 bits. Public key: a point (x, y), 64 bytes.
  • The same key pair signs transactions (ECDSA).

Purpose: prove ownership without revealing the secret (one-way: ECDLP).

Keccak-256 · 2008

Hash function for the address

The 64 bytes x ‖ y of the public key are hashed and only the last 20 bytes (160 bits) are kept.

  • Shortens the identifier and removes the algebraic structure of the curve point.
  • It is the original Keccak, not the NIST standard SHA3-256 (different padding, different output).

Purpose: a short, uniform, collision-resistant account identifier.

EIP-55 · 2016

Mixed-case checksum encoding

Hash the lowercase hex address with Keccak-256; write the i-th letter in upper case if the i-th hex digit of that hash is ≥ 8.

  • The 160 bits do not change: only the spelling does.
  • A mistyped address is rejected with probability ≈ 99.98%.

Purpose: detect typing errors. It adds no secrecy.

Both are hard to invert, but a hash has no key pair: nothing can be "verified" with it. The algebraic structure that makes kG a bad hash is what makes signatures possible.

3.2 Key derivation functions vs raw entropy and private keys

Raw entropy / private keys

Secret data. The entropy is generated by a cryptographic random generator: 128 unpredictable bits. It is the only place where randomness enters the pipeline.

KDF / HD derivation (PBKDF2, HMAC-SHA512)

Deterministic functions. Same input, same output, always. They transform a secret into other secrets that look unrelated, but they create no entropy.

Consequence: a 512-bit seed derived from a 12-word phrase can take at most 2128 values. Output length is not security. PBKDF2 is slow on purpose (2048 iterations) to make guessing phrases more expensive; HMAC-SHA512 in BIP-32 is fast because its input is already a strong secret.

The address cannot be turned back into the public key (it is a truncated hash), and the public key of an account becomes visible on chain only when the account signs its first transaction. Raw and checksummed addresses are the same address: EIP-55 is a way of writing, not a new value.

4. Historical context and why so many algorithms

  1. 1977 — RSA, the first practical public-key system (not used in Ethereum)
  2. 1985 — Elliptic-curve cryptography (Koblitz, Miller)
  3. 2000 — secp256k1 defined (SEC 2); PBKDF2
  4. 2001 — SHA-2 family (SHA-256, SHA-512)
  5. 2009 — Bitcoin: chooses secp256k1 and SHA-256
  6. 2012 — BIP-32; Keccak wins the SHA-3 competition
  7. 2013 — BIP-39
  8. 2014 — BIP-44
  9. 2015 — Ethereum mainnet (July); SHA-3 standard (August)
  10. 2016 — EIP-55

The BIPs were written "backwards". BIP-32 solved a technical problem (many keys from one seed), BIP-39 a human one (backing up that seed on paper), BIP-44 an interoperability one (which branch to use). Each standard answered a new need.

Why Keccak-256 and not SHA3-256. Ethereum was designed in 2013–14 with the winning Keccak submission. NIST published the final SHA-3 in August 2015 with a different padding, a few days after Ethereum's launch. Changing would have altered every address.

Why both SHA-2 and Keccak. The reason is historical, not technical: the BIPs come from Bitcoin (SHA-2 world), the address format from Ethereum (Keccak world).

SHA-2 / SHA-512 and Keccak / SHA-3

SHA-2 (SHA-256, SHA-512)Keccak / SHA-3

They share a name and a purpose but not a design: SHA-3 was chosen to be structurally different from SHA-2, as an insurance, and it did not replace it. Three names that are not synonyms: Keccak is the design, SHA-3 is NIST's standardised version, Keccak-256 is the pre-standard variant Ethereum uses. For the empty input, Keccak-256 gives c5d24601… while SHA3-256 gives a7ffc6f8….

Why several techniques instead of one

NeedProperty requiredProvided by
A person must be able to back up the secretreadable, with error detectionBIP-39 word encoding

No single algorithm has all these properties, and some of them exclude each other: signatures need the structure that an identifier must not have. Keeping the layers separate also means that a weakness in one piece can be replaced without redesigning the rest.

Experiment A — Avalanche effect of Keccak-256

2000 random 64-byte inputs (the size of a public key) are hashed; then one single bit of each input is flipped and the two 256-bit digests are compared. If every output bit flips with probability ½ independently, the number of changed bits is Binomial(256, ½): mean 128, standard deviation 8.

Histogram of the number of output bits changed (out of 256)

Experiment B — Are addresses uniform?

1000 random private keys are turned into addresses (secp256k1 → Keccak-256 → EIP-55). The 40 000 hex characters should be uniform over the 16 symbols (χ² with 15 degrees of freedom, rejected above 25.0). Each character is a letter a–f with probability 6/16, so the number of letters per address is Binomial(40, 3/8), and EIP-55 should write each letter in upper case with probability ½.

Experiment C — How strong are the two checksums?

BIP-39. The last word of the phrase above is replaced by each of the 2048 words of the list. With 12 words the checksum is 4 bits, so only one word in 24 = 16 should be accepted: a typing error has about a 6% chance of going unnoticed.
EIP-55. 100 000 random addresses are written with random upper/lower case. Each character is a digit (probability 5/8, always fine) or a letter with the right case (probability 3/8 · ½), so a random spelling passes with probability (13/16)40 ≈ 0.0247%.

An address has 15 letters on average, so one might expect 2−15 ≈ 0.003%. The real value is eight times larger, because the average is dominated by the addresses with few letters, which are weakly protected: E[2−L] > 2−E[L] (Jensen's inequality).

What these tests cannot tell. Uniform-looking outputs detect a broken component; they do not certify a secure one. A wallet whose random generator has only 32 bits of entropy produces phrases, keys and addresses that pass every test on this page, and can still be emptied by trying all 232 seeds. It happened: Milk Sad (2023). Security depends on how many inputs are possible, not on how the outputs look.
